**Статус разработки:** экспериментальный проект. Руководство сверено с исходным кодом, но не с успешной сборкой или сквозным запуском. Это не аудит безопасности и не подтверждение готовности к эксплуатации. Начните с одноразовых тестовых значений и прочитайте [заметки о безопасности](#безопасность), прежде чем подключать реальные аккаунты.

## Стек

| Ядро | Десктоп | Хранение | Интеграции |
|:--|:--|:--|:--|
| **Go**<br>CLI и локальные шлюзы | **Wails v2**<br>React · TypeScript · Vite | **SQLite**<br>Шифрование значений секретов · системное хранилище ключей | **HTTP(S) · LLM · MCP**<br>Исходящий прокси и stdio-обёртка |

## С чего начать

| Задача | Команда | Важное отличие |
|:--|:--|:--|
| Сохранить секрет и обращаться к нему по имени | `init`, `add`, `ls` | Само хранение не защищает другие приложения. |
| Проверить файл или текст | `scan` | Показывает находки, но не изменяет и не очищает исходные данные. |
| Запустить программу с поддержкой прокси | `run -- <команда>` | Запускает исходящий прокси и задаёт переменные прокси/CA. Это не песочница. |
| Подключить локальный MCP-сервер | `mcp run --mode inject -- <команда>` | Заменяет ссылки в окружении дочернего процесса настоящими секретами. Процессу нужно доверять. |
| Оставить ссылки в окружении MCP-сервера | `mcp run --mode proxy -- <команда>` | Нужны отдельно запущенный исходящий прокси и совместимый клиент. |

[Десктопная оболочка](cmd/sentinel-gui) предоставляет управление хранилищем, сканирование и редактирование политик. Она не заменяет запуск и подключение CLI-шлюзов. В этом руководстве записи создаются через CLI: соглашения об именах и метаданные привязки к хостам в GUI и CLI сейчас различаются.

## Установка

### Готовые файлы релиза (Go не нужен)

Скачайте архив под свою платформу со страницы GitHub Releases (`sentinel_<версия>_<ОС>_<архитектура>.tar.gz`/`.zip`), распакуйте, проверьте контрольные суммы и версию:

```bash
sha256sum -c checksums.txt
./sentinel version
```

Homebrew и Scoop описаны в [`packaging/`](packaging/README.md):

```bash
brew tap Ferrum-Sidereum/sentinel && brew install sentinel
```

```powershell
scoop bucket add sentinel https://github.com/Ferrum-Sidereum/scoop-sentinel
scoop install sentinel
```

### CLI из исходников

Понадобятся Git, версия Go из [go.mod](go.mod) и доступ к системному хранилищу учётных данных. Сейчас модуль указывает **Go 1.27.0**.

```bash
git clone https://github.com/Ferrum-Sidereum/sentinel.git
cd sentinel
go version
go mod download
go install ./cmd/sentinel
```

`go install` помещает исполняемый файл в `GOBIN`, а если переменная не задана, в каталог `bin` первого пути из `GOPATH`. Добавьте этот каталог в `PATH`. Сборка из исходников необязательна — готовые файлы доступны на странице релизов.

### Разработка десктопа (необязательно)

Установите Node.js/npm и нативные зависимости Wails v2 для своей платформы. Используйте закреплённую в репозитории версию Wails:

```bash
go install github.com/wailsapp/wails/v2/cmd/wails@v2.15.0
cd cmd/sentinel-gui
wails doctor
wails dev
```

Для сборки приложения выполните `wails build` в том же каталоге. Wails вызывает команды установки и сборки фронтенда из [wails.json](cmd/sentinel-gui/wails.json). В рамках этого изменения документации данный сценарий не запускался.

## Быстрый старт

### 1. Инициализируйте локальное хранилище

```bash
sentinel init
```

Команда создаёт данные в `~/.sentinel` (в домашнем каталоге текущего пользователя), включая `vault.db` и начальный `policy.yaml`. В штатном сценарии мастер-ключ хранится в системном хранилище ключей.

**Без keychain:** используйте `sentinel init --passphrase`. Парольная фраза каждый раз читается с терминала без эха (двойное подтверждение при создании) и **нигде не хранится** — в `~/.sentinel/key.json` (mode `0600`) лежат только параметры KDF, случайная соль и проверочное значение. Потеря фразы = потеря vault. Без флага `--passphrase` отсутствующее хранилище ключей — жёсткая ошибка. Миграция старого файла: `sentinel migrate-key`.

### 2. Добавьте тестовый секрет

```bash
sentinel add demo_token --bind api.example.com --header Authorization --kind bearer
```

В ответ на `value:` введите вымышленное значение, а не настоящий ключ:

```text
sentinel-demo-value-1234567890
```

```bash
sentinel ls
```

Имя записи: `demo_token`, каноническая ссылка: `snt://demo_token`. `api.example.com` здесь только пример привязки, а не рабочий тестовый API. Для реальной интеграции указывайте только нужное имя хоста API, без схемы и пути. Команда читает значение из stdin, но интерактивный ввод не скрывается.

Прокси заменяет текст в уже сформированном запросе; `--kind bearer` не создаёт заголовок Authorization автоматически. Совместимый запрос должен явно содержать `Authorization: Bearer snt://demo_token`.

### 3. Проверьте текст или файл

```bash
# macOS / Linux: проверка тестового значения через stdin
printf '%s\n' 'sentinel-demo-value-1234567890' | sentinel scan
```

```powershell
# Windows PowerShell
'sentinel-demo-value-1234567890' | sentinel scan
```

Либо создайте UTF-8-файл `sample.txt` с этим тестовым значением и выполните:

```bash
sentinel scan sample.txt
```

При исправном инициализированном хранилище ожидается совпадение с известным значением, указанием детектора и оценки уверенности. **Вывод CLI содержит сам найденный текст.** Не копируйте результаты с настоящими секретами в задачи, чаты или логи CI. Отсутствие находок не доказывает безопасность текста; у `scan` также нет документированного контракта кодов завершения для блокировки CI при утечке.

### 4. Запустите программу через исходящий прокси

При установленном curl:

```bash
sentinel run -- curl https://example.com
```

В Windows PowerShell при необходимости используйте `curl.exe` вместо `curl`. Это пробная проверка маршрутизации без учётных данных, а не тест подстановки секретов. Нужны доступ к сети и свободный локальный порт `18449`.

`run` запускает прокси на `127.0.0.1:18449`, задаёт `HTTP_PROXY`, `HTTPS_PROXY` и `SSL_CERT_FILE` (а также переменные прокси в нижнем регистре) и запускает дочерний процесс. Команда **не** заполняет его окружение ссылками на все записи хранилища. Передавайте только те ссылки, которые действительно нужны приложению.

Через Sentinel пойдут только клиенты, учитывающие эти настройки прокси. Для HTTPS перехват выбирается по хостам, привязанным к секретам; остальные HTTPS-соединения туннелируются без анализа содержимого. Для перехватываемых соединений клиент должен доверять `~/.sentinel/ca.pem`. Некоторые клиенты игнорируют `SSL_CERT_FILE` и требуют собственной настройки CA. Не отключайте проверку TLS ради устранения ошибки сертификата.

`sentinel trust-ca` меняет хранилище корневых сертификатов текущего пользователя Windows через `certutil`; это не универсальный шаг установки. Во время оценки проекта лучше доверять сертификату только в нужном клиенте. Не запускайте `serve` и `run` одновременно на одном порту.

### 5. Подключите локальный MCP-сервер

Сначала отдельно установите и проверьте выбранный MCP-сервер. Sentinel его не устанавливает. В примере Node.js и `/absolute/path/to/server.js` обозначают **уже существующий доверенный stdio MCP-сервер**. Замените программу, путь и имя переменной окружения на требуемые вашим сервером.

Для MCP-клиента с конфигурацией `mcpServers`:

```json
{
  "mcpServers": {
    "sentinel-demo": {
      "command": "/absolute/path/to/sentinel",
      "args": ["mcp", "run", "--mode", "inject", "--", "node", "/absolute/path/to/server.js"],
      "env": {
        "API_TOKEN": "snt://demo_token"
      }
    }
  }
}
```

В Windows укажите абсолютный путь к `sentinel.exe` и экранируйте обратные косые черты в JSON. Абсолютный путь помогает избежать различий между `PATH` в терминале и окружением десктопного клиента.

Эквивалентный синтаксис запуска в POSIX-оболочке:

```bash
API_TOKEN='snt://demo_token' sentinel mcp run --mode inject -- node /absolute/path/to/server.js
```

Команда общается по MCP через stdin/stdout, а не открывает интерактивный чат. Сервер в ожидании сообщений клиента может выглядеть бездействующим. Режим `inject` заменяет ссылку настоящим значением в окружении дочернего процесса только после одобрения брокером (approval required by default): правило `approvals` в `policy.yaml` (`default: ask|allow|deny`, `rules`, `grant_cache`, `max_uses_per_minute`) или интерактивный запрос `[o]nce / [s]ession / [1]5m / [d]eny`; отказ оставляет `snt://`-ссылку как есть (`--strict` завершает с кодом 4), `--yes-i-know` разрешает всё (только демо/тесты). Обёртка фильтрует поддерживаемые текстовые поля MCP, а не произвольный вывод или stderr дочернего процесса.

Для режима `proxy` запустите исходящий прокси в отдельном терминале:

```bash
sentinel serve 127.0.0.1:18449
```

Затем запускайте MCP-обёртку из клиента с `--mode proxy`, сохранив ссылки в переменных окружения и настроив дочернюю программу на `http://127.0.0.1:18449` и нужное доверие к CA. `mcp run --mode proxy` сам этот прокси не запускает. Перед использованием проверьте, что запросы клиента действительно проходят через него.

Дополнительные шаблоны: [конфигурация Claude Desktop](examples/claude_desktop_config.json) · [конфигурация Cursor](examples/cursor_mcp.json). Перед использованием проверьте пути, пакеты серверов, имена переменных для токенов и границы доверия. Это примеры, а не проверенные готовые интеграции.

## Локальные данные и настройки

| Расположение | Назначение |
|:--|:--|
| `~/.sentinel/vault.db` | Хранилище секретов. |
| Системное хранилище ключей, сервис `sentinel-master` | Штатное хранение мастер-ключа CLI. |
| `~/.sentinel/key.json` | Параметры KDF, случайная соль, verifier (без секретов), mode `0600`. Парольная фраза не хранится. |
| `~/.sentinel/policy.yaml` | Настройки фильтрации. |
| `~/.sentinel/audit.jsonl` | Локальные события аудита поддерживаемых операций. |
| `~/.sentinel/ca.pem` | Сертификат локального CA для перехватываемого HTTPS. |
| `~/.sentinel/passphrase` (legacy) | Старый файл открытым текстом; больше не создаётся и не читается. Мигрируйте через `sentinel migrate-key`, удаляющим его после проверенного перешифрования. |

Безопасно резервируйте хранилище вместе с соответствующим ключевым материалом. Не коммитьте каталог данных, учётные данные или закрытые ключи CA. Копия базы без соответствующего ключа не обеспечивает восстановление. Начальная политика содержит настройки туннелирования неизвестных хостов, псевдонимизации для LLM и маскирования для недоверенных получателей; какие шлюзы реально применяют каждое поле, показывает `sentinel policy explain`. Прежде чем полагаться на правило, проверьте нужную реализацию.

## Безопасность

- **Парольная фраза не хранится:** `sentinel init --passphrase` читает фразу с терминала без эха, в `key.json` (mode `0600`) — только параметры KDF, случайная соль и verifier. Потеря фразы = потеря vault. Старый файл `passphrase` открытым текстом больше не используется; миграция — через `sentinel migrate-key`.
- **Секреты могут попасть в процессы и терминал.** MCP `inject` намеренно передаёт дочернему процессу настоящие значения. Ввод `add` может отображаться, `scan` печатает совпадения, stderr MCP-сервера передаётся без изменений.
- **Всеобщая очистка не гарантируется.** MCP-фильтрация охватывает выбранные текстовые поля JSON. HTTPS-туннели для непривязанных хостов не анализируются. Кодированные данные, неподдерживаемые протоколы и обход прокси требуют отдельных проверок. Подстановка в прокси не заменяет полноценную систему предотвращения утечек.
- **У привязок есть ограничения.** Подстановка в окружение MCP не проверяет привязки прокси, а список разрешённых заголовков не гарантирует запрет подстановки в URL или тело запроса. Используйте тестовые ключи с минимальными правами и проверяйте именно свой сценарий.
- **Оставляйте слушающие адреса локальными.** Используйте loopback, а не `0.0.0.0` или публичный интерфейс. Не публикуйте прокси в сети без отдельной проверки безопасности.
- **Доверие к CA расширяет границу доверия.** Установка корневого сертификата влияет на безопасность соединений. Защищайте закрытые ключи CA и предпочитайте доверие в отдельном клиенте. Не используйте `--insecure` как исправление установки.
- **GUI и CLI пока не взаимозаменяемы.** Записи из десктопа используют другое соглашение об именах и не содержат метаданных привязки к хосту из CLI. Для этого руководства используйте CLI на всех этапах; не считайте, что прокси автоматически подставит запись из GUI.

## Проверки при разработке

Из корня репозитория, с установленной требуемой версией Go:

```bash
go build ./cmd/sentinel
go test ./internal/... ./cmd/sentinel
go vet ./internal/... ./cmd/sentinel
```

Отдельно для фронтенда:

```bash
cd cmd/sentinel-gui/frontend
npm ci
npm run typecheck
npm run build
```

Для проверок десктопа нужны нативные зависимости Wails и собранные ресурсы фронтенда. Выполните `wails doctor` и `wails build` из `cmd/sentinel-gui`, затем запускайте тесты GUI-пакета в подготовленной среде. Команды выше являются инструкцией по проверке, а не зафиксированными успешными результатами. В рамках этого изменения документации Go-тесты, десктоп и реальный API/MCP-трафик не запускались и не проверялись.

## Если что-то не работает

| Симптом | Что проверить |
|:--|:--|
| Команда `sentinel` не найдена | Добавьте каталог установки Go в `PATH`; в MCP-клиенте укажите абсолютный путь. |
| Не скачивается Go или зависимость | Проверьте доступность версий из `go.mod` и сетевой доступ к источникам модулей. |
| Инициализация просит парольную фразу | Не добавляйте реальные ключи; восстановите доступ к системному хранилищу вместо небезопасного резервного сценария. |
| Порт занят | `run` использует `18449`; не запускайте второй исходящий прокси на этом порту. |
| Ошибка проверки TLS | Настройте доверие клиента к локальному CA, не отключая проверку сертификатов. |
| MCP выглядит зависшим | Запускайте его из MCP-клиента; проверьте программу сервера, абсолютные пути и имена переменных окружения. |
| Ссылка не заменяется | Убедитесь, что запись создана через CLI, имя совпадает, а нужный режим подстановки или маршрут через прокси включён. |

Текущая справка CLI без аргументов перечисляет только часть команд и не является полным справочником.
